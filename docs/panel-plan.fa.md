# نقشهٔ توسعهٔ پنل

## محدودهٔ مرحلهٔ اول

پوستهٔ مستقل و سبک با React و TypeScript: منوی فارسی، هدر، فوتر، مسیرهای پایدار و منوی موبایل. محتوای صفحات فعلاً وضعیت آماده‌سازی را نشان می‌دهد. هیچ درخواست نوشتنی، فرم اجرای دستور، اتصال آماری، نمودار یا صفحهٔ ورود در این مرحله فعال نیست.

## ساختار صفحات

| صفحه            | مسیر              | هدف مرحله‌های بعد                                      |
| --------------- | ----------------- | ------------------------------------------------------ |
| نمای کلی        | `/`               | وضعیت واقعی روزها، رکوردها، مراحل و سلامت worker       |
| روزها و چانک‌ها | `/days`           | انتخاب روز و چانک، پوشش جزئی/کامل و مرحلهٔ پردازش      |
| مرور داده‌ها    | `/data`           | فیلتر و جست‌وجوی سمت سرور، صفحه‌بندی و جزئیات رکورد    |
| عملیات و پردازش | `/operations`     | کاتالوگ عملیات فعلی، پارامترهای معتبر و ثبت job        |
| صف اجراها       | `/jobs`           | وضعیت و جزئیات job، لاگ افزایشی و خطا                  |
| تصویر و نمودار  | `/visualizations` | تولید در زمان درخواست و مشاهدهٔ خروجی‌های قبلی         |
| گزارش‌ها        | `/reports`        | گزارش روز، چانک، گره، مولفه و فرامولفه، مقایسه و خروجی |
| مدل و رفتار     | `/models`         | نسخهٔ مدل، مرجع نرمال، پوشش سیگنال و انحراف رفتاری     |
| تنظیمات         | `/settings`       | تنظیمات پنل و سیاست دسترسی پس از تصمیم استقرار         |

مسیرهای فعلی در URL پس از `#` قرار می‌گیرند. انتخاب آیندهٔ روز/چانک/اجرا باید در query مسیر نگهداری شود تا لینک‌ها قابل اشتراک و بازگشت باشند. شناسهٔ چانک پارتیشن پردازش است و نباید خودکار ساعت/دقیقه تفسیر شود.

## بررسی API موجود

بررسی بر اساس `api/urls.py`، `api/views.py`، `api/serializers.py` و `api/registry.py` در برنچ `main`، کامیت `1e8e302` انجام شده است. این فایل‌ها بخشی از برنچ مستقل `panel` نیستند؛ اتصال آینده از طریق REST API سرویس جداگانه خواهد بود.

| قابلیت                 | API فعلی                                                 | ملاحظات                                                                              |
| ---------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| سلامت MongoDB و worker | `GET /api/v1/health/`                                    | heartbeat و job جاری؛ وضعیت اتصال پنل باید از پاسخ واقعی بیاید                       |
| کاتالوگ عملیات         | `GET /api/v1/actions/`                                   | گزینه‌ها، defaults و choices از parser دستورهای موجود گرفته می‌شوند                  |
| اجرای عملیات           | `POST /api/v1/actions/<category>/<action>/`              | صف مستقل؛ پاسخ ۲۰۲ به معنای پایان اجرا نیست؛ پشتیبانی از Idempotency-Key             |
| اجراها                 | `GET /api/v1/jobs/` و `GET /api/v1/jobs/<id>/`           | صفحه‌بندی limit/offset و فیلتر status؛ فیلتر روز/چانک/مدل فعلاً موجود نیست           |
| لاگ                    | `GET /api/v1/jobs/<id>/logs/`                            | استفاده از next_offset بر حسب بایت، با حفظ متن UTF-8                                 |
| لغو                    | `POST /api/v1/jobs/<id>/cancel/`                         | فقط job در صف؛ توقف اجرای جاری پشتیبانی نمی‌شود                                      |
| روزها                  | `GET /api/v1/days/`                                      | تعداد رکورد خام؛ خروجی صفحه‌بندی دارد ولی تجمیع کامل روزها قبل از slice انجام می‌شود |
| چانک‌ها                | `GET /api/v1/days/<day>/chunks/`                         | شمارش نرمال‌شده، کاندید، نماینده، مولفه و مشخصات گراف؛ فعلاً بدون صفحه‌بندی          |
| خروجی‌ها               | `GET /api/v1/artifacts/` و `GET /api/v1/artifacts/file/` | محدود به document؛ لیست صفحه‌بندی دارد، پیمایش پوشه قبل از slice است                 |
| مستندات                | `/swagger/` و `/api/schema/`                             | فعلاً بدون احراز هویت                                                                |

کاتالوگ، عملیات ورود و نرمال‌سازی، ساخت گراف و نماینده، سلسله‌مراتب، طیف، یادگیری و رفتار را دارد. برخی عملیات تولید تصویر نیز موجودند، مثل visualize-representatives و visualize-encoder-metas؛ وجود این دستورها به معنای وجود API عمومی رسم هر انتخاب دلخواه نیست.

## جریان کار هدف

۱. انتخاب روز، چانک و اجرای علمی یا نسخهٔ مدل؛ حالت «هنوز انتخاب نشده» و «داده موجود نیست» صریح باشد.

۲. خواندن عملیات مجاز و پارامترها از کاتالوگ، نمایش محدوده و اثر دستور، سپس ثبت درخواست با کلید جلوگیری از تکرار. عملیات حذف، reset یا force قبل از ثبت، تأیید جداگانه با نام روز/چانک و اثر دقیق می‌خواهد. معنا و دامنهٔ force باید از همان دستور گرفته شود؛ force در همهٔ دستورها الزاماً حذف نسخهٔ قبلی نیست.

۳. رفتن به جزئیات job و polling با فاصلهٔ معقول؛ دریافت لاگ از next_offset، توقف polling در وضعیت نهایی و توقف/کاهش آن در تب مخفی. خطای شبکه نباید به ارسال دوبارهٔ عملیات منجر شود. درصد پیشرفت فقط وقتی نمایش داده شود که بک‌اند آن را معتبر گزارش کند؛ در غیر این صورت مرحله و وضعیت نامعین نشان داده شود.

۴. برای تصویر درخواستی، انتخاب کاربر هنگام ثبت به یک snapshot از پارامترها و شناسهٔ اجرا تبدیل شود. رسم در worker انجام شود، job برگردد و فقط پس از پایان موفق، manifest خروجی خوانده شود. تغییر انتخاب کاربر در حین اجرا نباید نتیجهٔ job قبلی را به انتخاب جدید نسبت دهد. آرشیو خروجی‌های قبلی مسیر جداگانه‌ای از «تولید خروجی جدید» دارد.

۵. هر نتیجه، تصویر، گزارش و export باید به job_id، شناسهٔ اجرای علمی، پارامترها، نسخهٔ داده، مدل/مرجع (در صورت کاربرد)، زمان و فایل‌های خروجی متصل باشد. job_id با شناسهٔ اجرای علمی یکی نیست. مقایسه فقط با نمایش سازگاری ویژگی‌ها، نرمال‌سازی و نسخه‌ها انجام شود؛ فضای نهفتهٔ دو مدل روزانه بدون هم‌ترازی قابل مقایسهٔ مستقیم نیست. انحراف رفتاری به‌خودی‌خود برچسب حمله نیست.

## نیازهای تکمیلی API — پیشنهاد، هنوز پیاده‌سازی نشده

| نیاز                | پیشنهاد قرارداد                                                                                                                                                                          |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| مرور رکوردهای حجیم  | endpointهای خواندنی allowlist برای نوع داده، فیلترهای تایپ‌شدهٔ روز/چانک، جست‌وجوی محدود، sort پایدار و cursor pagination؛ جزئیات با شناسهٔ رکورد؛ از پذیرش query خام MongoDB اجتناب شود |
| داشبورد مراحل       | خلاصهٔ نسخه‌دار هر روز/چانک همراه coverage و منابع شمارش؛ pagination و aggregation سمت MongoDB، ایندکس‌های متناسب و جلوگیری از بارگذاری کل داده                                          |
| اجراها و provenance | فهرست اجراهای علمی به تفکیک مرحله، روز، چانک و نسخه؛ ارتباط صریح با job، داده، مدل، reference و manifest                                                                                 |
| پیشرفت              | فیلد ساخت‌یافتهٔ phase و completed/total در صورت قابل محاسبه بودن؛ نباید از متن لاگ درصد فرضی استخراج شود                                                                                |
| رسم انتخاب فعلی     | action صف‌شده با پارامترهای محدود و معتبر سطح/شناسه‌های انتخاب، ارجاع به ورودی immutable و manifest خروجی؛ استفاده از سرویس‌های علمی موجود بدون محاسبهٔ سنگین در view                    |
| گزارش و مقایسه      | API خواندن manifestها و سنجه‌های ساخت‌یافته با واحد، تعریف، محدودیت و شناسهٔ اجرا؛ اعتبارسنجی سازگاری دو نتیجه پیش از مقایسه                                                             |
| خروجی گرفتن         | استفاده از فایل موجود؛ برای خروجی جدید و حجیم، job مستقل و دانلود صفحه‌بندی‌شده/جریانی پس از تکمیل                                                                                       |
| مدل و رفتار         | خلاصهٔ مدل و نسخه، مرجع نرمال، پوشش سیگنال‌ها، lineage و وضعیت‌های not_computed/insufficient_data؛ بدون تعبیر خودکار به حمله                                                             |
| استقرار واقعی       | تعیین احراز هویت، نقش خواندن/اجرا/حذف، audit، سیاست CSRF یا token و دسترسی فایل؛ تصمیم جداگانه پیش از انتشار عمومی                                                                       |

## ترتیب پیشنهادی پیاده‌سازی

۱. **پوسته (فعلی):** ساختار و ناوبری؛ بدون تغییر بک‌اند و منطق علمی.

۲. **مشاهدهٔ وضعیت واقعی:** سلامت، روزها، چانک‌ها، اجراها و لاگ؛ حالت بارگذاری، خطا، نبود داده و قطع ارتباط.

۳. **اجرای کنترل‌شده:** فرم‌های مبتنی بر کاتالوگ و قرارداد parser، تأیید عملیات حساس و پیگیری job.

۴. **مرور و provenance:** قراردادهای صفحه‌بندی، فیلتر، جزئیات و ارجاع خروجی به اجرای علمی.

۵. **تصویر، گزارش و مدل:** تولید صف‌شده برای انتخاب فعلی، آرشیو، مقایسهٔ معتبر و export.

قبل از فعال‌کردن هر مرحله، قرارداد API و نمونهٔ خروجی آن مشخص و با تست یکپارچه بررسی شود. دستورهای کنسولی و چارچوب علمی موجود مبنا می‌مانند.
